# 7.10 SDD 開發流程

全程以規格驅動開發（Spec-Driven Development）進行：**GDD 是規格，程式是規格的實作，測試是規格的驗證。**

## 原則

1. **文件為準**：任何行為都必須能在 GDD 中找到依據。找不到的行為，先寫進文件再實作。
2. **衝突先改文件**：實作時發現文件錯誤、矛盾、不可行，先修改文件（必要時記入 7.9），再改程式。不得讓程式「默默」偏離文件。
3. **可追溯**：每個工作項目、每段程式、每個測試，都能對應到 GDD 的節號。
4. **驗收即規格**：里程碑的驗收標準就是完成的定義；未通過不得宣告完成。

## 規格編號

- 規格以 GDD 節號指稱，例如 `GDD 3.5`。
- 需要指到更細的條文時，用「節號 + 小標題」，例如 `GDD 3.5 天劫`。不建立三層節號（1.4 規則 11）。
- 參數以 8.1 的代號指稱，例如 `REALM_EXP`。

## 流程（每個里程碑）

```
① 規格確認 ─▶ ② 任務拆解 ─▶ ③ 實作 ─▶ ④ 驗證 ─▶ ⑤ 收尾
     ▲                         │         │
     └──── 發現規格問題：先改文件 ◀─┴─────────┘
```

| 步驟 | 做什麼 | 產出 |
|---|---|---|
| ① 規格確認 | 重讀該里程碑（7.x）與其依據章節；列出不清楚、矛盾、缺數值之處，先修文件 | 文件修正的 commit（`docs:`） |
| ② 任務拆解 | 在該里程碑文件的「任務與追溯」表中，列出每個工作項目、對應節號、驗證方式 | 更新後的 7.x |
| ③ 實作 | 依任務實作；程式中標註規格來源 | 程式 commit（`feat:`、`fix:`），訊息中引用節號 |
| ④ 驗證 | 跑測試、`siming-cli` 報表、截圖；逐條勾選驗收標準 | 驗證紀錄（附在里程碑文件的「驗收紀錄」） |
| ⑤ 收尾 | 更新 7.1 狀態、7.9 決策；推送 | 里程碑完成的 commit |

## 程式中的規格標註

- 每個模組的檔頭註明對應的 GDD 節號：

  ```rust
  //! GDD 3.5 道：修煉與天劫
  ```

- 實作特定規則的函式，以文件註解標註：

  ```rust
  /// GDD 3.5 天劫：渡劫存活率。
  ```

- 數值一律引用 `params.rs` 中與 8.1 同名的常數，不寫魔術數字。

## 測試與規格的對應

- 測試名稱包含節號或參數代號，例如 `gdd_3_5_tribulation_survival_matches_formula`。
- 每個里程碑的驗收標準，在「任務與追溯」表中標明由哪個測試或報表驗證。
- 平衡目標（8.1）由 `siming-cli sim --report` 輸出，並由 `balance` 測試比對。

## 規格變更

| 變更類型 | 流程 |
|---|---|
| 錯字、說明不清、補充細節（不改行為） | 直接修文件 |
| 數值調整（平衡） | 修 8.1，必要時同步章節；commit 訊息說明依據（報表） |
| 行為改變、新增或刪除機制 | 修章節與 8.1；記入 7.9 決策紀錄；若影響已完成的里程碑，重跑其驗收 |
| 範圍改變（加入或移出某里程碑、Demo） | 修 7.x、10.1；記入 7.9；需使用者確認 |

## AI 代理分工

開發盡量交由 Haiku 與 Sonnet 子代理執行；主控為 Opus（主對話），負責規格與整合，同時也在升級鏈中；Opus 也解不了的難題，再升級到 Fable。

模型以家族名稱指稱（Haiku、Sonnet、Opus、Fable），不限定版本；一律使用各家族當時的最新版本。

| 角色 | 模型 | 負責 | 不做 |
|---|---|---|---|
| 主控 | Opus（主對話） | 步驟①規格確認與文件修改；②任務拆解與指派；整合與衝突處理；確定性相關審查；④驗收判定；⑤收尾 | 大量重複性實作 |
| 實作者 | Sonnet | 依任務實作模組：世界生成、模擬系統、Bevy 渲染、著色器、介面；為自己的模組寫測試；除錯 | 修改文件；更動任務範圍外的模組 |
| 審查者 | Sonnet | 對照規格審查實作：行為、數值引用、確定性規則（6.5）；回報不符之處 | 直接改程式（由實作者或主控修） |
| 難題 | Fable | 升級鏈最上層：演算法設計、確定性錯誤、著色器與渲染除錯、效能瓶頸、跨模組重構中，Opus 也未能解決者 | 例行實作 |
| 助手 | Haiku | 機械性工作：依 8.1 抄寫 `params.rs`；字庫與模板 JSON；`t2s.py` 產生簡體版；文件連結與追溯表檢查；搜尋魔術數字；`siming-cli` 報表整理；fmt 與 clippy 修正；樣板測試 | 設計判斷；規格解讀有歧義的工作 |

### 規則

1. **指派**：每個子代理的任務描述都要列出依據的 GDD 節號、可修改的檔案範圍、驗收方式。
2. **平行**：實作者以獨立 worktree 平行作業，任務切分到互不重疊的模組或檔案；由主控合併。
3. **衝突回報**：子代理發現規格不清、矛盾或不可行時，停止並回報，不得自行改變行為。主控依「規格變更」流程先改文件，再重新指派。
4. **驗證分離**：實作與審查由不同的子代理擔任；驗收由主控判定。
5. **升級路徑**：Haiku → Sonnet → Opus（主控）→ Fable。
   - 純抄寫、格式化、檢查類工作，一律交給 Haiku。
   - 一般實作與審查交給 Sonnet。
   - Sonnet 兩次嘗試仍未通過驗證的任務，由 Opus 親自處理。
   - 以下情況再升級到 Fable：Opus 處理後仍未通過；問題涉及確定性、渲染管線、效能，且根因不明；需要重新設計演算法。
   - 升級時附上前一層的嘗試紀錄與失敗證據。

## Commit 規範

| 前綴 | 用途 |
|---|---|
| `docs:` | 只改文件 |
| `feat:` | 新功能（引用節號） |
| `fix:` | 修正實作與規格不符 |
| `test:` | 只改測試 |
| `chore:` | 建置、CI、工具 |
| `balance:` | 只改 8.1 數值與 `params.rs` |

同一個 commit 不同時包含「文件行為變更」與「程式實作」：先 `docs:`，再 `feat:` 或 `fix:`。
